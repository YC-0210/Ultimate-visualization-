Capture guards

Every read in the middleware that can raise, what it raises, and the guard. Check this card whenever you add a probe.

The rule

Call the original outside the guard. Guard only what you do with the result. Then: swallow with except Exception, and record the failure so absence never has to mean two things.

Shape

result = original(...)          # outside — the app's work
try:
    ...our bookkeeping...       # inside
except Exception as exc:        # not bare except
    note_failure("where", exc)  # swallow AND record
return result                   # always reachable

Every site, and what it raises

SiteCan raiseGuard
request.body
P1.1		 RequestDataTooBig over DATA_UPLOAD_MAX_MEMORY_SIZE (2.5 MB default); RawPostDataException if the stream was already read; UnreadablePostError if the client cancels an upload; UnicodeDecodeError on non-text bytes. except Exception, not just UnicodeDecodeError. Record "<body not captured>".
response.content
P1.6		 AttributeError on any StreamingHttpResponse — including FileResponse, which is what django.views.static.serve returns for /media/…, and what Phase 3's own SSE endpoint will be. Branch on response.streaming before touching .content. Never consume streaming_content.
capture_sql append
P1.5		 Anything from list(params) or the timing maths. The danger is not the exception, it is losing return result — the query's own return value. result = execute(...) first, guard the append, return result last.
probed_is_valid append
P1.7		 encode() meeting a value whose str() raises; dict(self.validated_data) on an unusual serializer. Guard the append only. Runs inside the view, so Django's middleware-boundary conversion does not apply here.
probed_render append
P1.8		 Same as above, plus self.template.name and dict(context) when the context is not a plain dict. Guard the append only. Same reason.
the trace file write
P1.9		 OSError — no permission, disk full, read-only volume. AttributeError on settings.BASE_DIR: that name comes from the startproject template, so a project that does not define it has no such setting. Guard the whole write. A trace that cannot be saved is not a reason to fail the request.

Exception, not BaseException

Python's docs on Exception: “All built-in, non-system-exiting exceptions are derived from this class.” KeyboardInterrupt and SystemExit derive from BaseException, so they are not caught — which is what you want in code that runs on every request. A bare except: catches them and eats Ctrl-C.

What you do not guard

Not thisWhy
self.get_response(request) Django already converts view and inner-middleware exceptions into responses before your code resumes, so “every middleware can always rely on getting some kind of HTTP response back” (Exception handling). Guard it and a firing guard leaves you with no response to return.
original_is_valid(...), original_render(...) These are the app's work. Swallowing here turns a real validation or template error into a silent success, and the view carries on with a wrong result.
the finally restore It must run, and it must not be skipped. Leave the probe installed and the next request wraps the wrapper.

The mark

"capture_errors": [
  {
    "where": "render",
    "error": "TypeError: keys must be str, not tuple"
  }
]

Usually []. It exists because an absent stage already means “did not happen” — so a swallowed probe failure needs a different shape in the file, or the panel states a fact nothing observed (D2). Prior art: the Sentry SDK's capture_internal_exceptions() swallows from the host app and logs for the tool's author.
