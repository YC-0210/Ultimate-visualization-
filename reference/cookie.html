Cookie — ticket card

The number on the ticket the diner keeps and brings back. Not the diner’s name. Sources: MDN: Using HTTP cookies, Django sessions.

Two headers, two directions

HeaderWho sends itOn this project
Set-Cookie Server → browser (the response) Waiter hands the diner a ticket. You do not print this yet (P1.6).
Cookie Browser → server (the next request) Diner puts the ticket on the table. You already dump this in headers.

MDN: a cookie is “a small piece of data a server sends to a user’s web browser. The browser may store cookies … and send them back to the same server with later requests.” HTTP is stateless by default — each request is a stranger unless that ticket comes back.

What Django puts on the ticket

Django’s session docs: “Cookies contain a session ID – not the data itself.” The default name is sessionid. The session dictionary stays on the server. The ticket only has the lookup number.

You may also see csrftoken= in the same Cookie header. That is a different ticket for a different job. P1.3 cares about sessionid.

What you can see today

P1.1 already prints request headers. Look for Cookie. First visit: often missing. After the homepage writes table_number into the session, the next request in the same browser should show sessionid=….
