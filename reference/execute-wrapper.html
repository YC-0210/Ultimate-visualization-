execute_wrapper

Django’s hook for seeing SQL as it runs. Source: Database instrumentation.

What it is

A context manager on the thread-local connection. Enter: install a wrapper around every query. Exit: remove it. Docs: wrappers are modeled after middleware — a callable that takes another callable.

The five arguments

NameWhat it is
execute Callable. You must call execute(sql, params, many, context) and return that result.
sql A str. The SQL to send. Placeholders, not interpolated values.
params List/tuple of bound values, or a sequence of those for executemany().
many bool. Whether this is execute() or executemany().
context A dict with the connection and cursor. Do not dump it — live objects.

Where P1.5 installs it

with connection.execute_wrapper(capture_sql):
    response = self.get_response(request)

Around get_response, not after. SQL from inner middleware and the view runs inside that call.

Not this

HookWhy not P1.5
connection.queries Only populated when DEBUG is True. FAQ.
queryset.model P1.4. A class name on the view. Not the SQL that ran.

JSON shape

"sql": [
  {
    "sql": "SELECT …",
    "params": ["經典原味鍋"],
    "duration_ms": 0.4
  }
]

Keep sql and params separate. duration_ms is milliseconds around the execute call (time.monotonic(), as in Django’s QueryLogger example).
