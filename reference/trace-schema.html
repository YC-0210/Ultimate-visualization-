Why sql is not simply query_data

On a real GET /menuitem/經典原味鍋/ the wrapper caught five queries. Only three are the view's data reads (menuitem, meattype, hotpotingredients). The other two are machinery: the django_session row and the auth_user row, fetched because something touched request.session and request.user.

execute_wrapper is told the SQL, not the caller. Nothing in Phase 1 records which stage caused a query, so claiming per-stage attribution would be inventing a fact (D2). Keep sql as one top-level list in the order it fired. Attribution needs the SQL probe to know the current stage — the context propagation D6 bought, wired in when stages nest.

Rule

CONTEXT: which stages exist is a property of the endpoint. An empty probe list means omit that kind. Do not keep a Django key with [] so a second adapter would have to invent the same key.
