The model name vs the SQL that ran

You already know which model the view is configured for. You do not yet see the SQL Django actually sent to the database.

Where this fits Roadmap: Phase 1, P1.5 — capture SQL with connection.execute_wrapper. P1.4 read queryset.model without running a query. Today you copy each query as it runs. See where this sits on the map →

The problem

Same real request: GET /api/menuitem/經典原味鍋/. One view. Two facts.

Already have · P1.4

The model on the view class

The class name. Reading it did not run SQL.

restaurantAPI.models.menuitem

Missing · P1.5

The SQL that actually ran

The string Django sent to the database for this request.

SELECT … FROM restaurantAPI_menuitem WHERE slug = %s

One short analogy for the new idea: Python and the database do not share a language. The view says menuitem and slug 經典原味鍋. Django translates that lookup into a sentence the database can read. That sentence is Type: a str — the SQL query to be sent to the database. Django passes it to your wrapper together with params (the bound values) and execute (the callable that actually runs it). Database instrumentation .

Same wrap, one layer down

Middleware already wraps the view: call get_response, then do something around it. Django’s instrumentation docs say SQL wrappers are Meaning: built to work like. Not a Django Model (that is menuitem). Django’s docs: wrappers “are modeled after middleware – they are callables which take another callable as one of their arguments.” Middleware takes get_response and calls it. The SQL wrapper takes execute and calls it. Same shape. Database instrumentation after middleware. Same shape, smaller job: wrap Type: a callable. Invoke it with sql, params, many, and context to run the query. Like get_response: if you do not call it, the next step never happens. The wrapper must return whatever execute returned. Database instrumentation instead of the view.

wrapper around get_response with connection.execute_wrapper(…):
  • SELECT … django_session … May appear: SessionMiddleware can query the session inside get_response.
  • SELECT … restaurantAPI_menuitem WHERE slug = %s The view’s lookup. params holds 經典原味鍋 — the same slug you already dump in kwargs.

Install around get_response, not after it. SQL runs inside that call — inner middleware and the view. After it returns, those queries have already happened. The wrapper is a context manager: on for that block, then off.

Why not connection.queries

Django’s FAQ will give you a list of SQL at connection.queries. That list is only filled when DEBUG is True. P1.5 needs a probe that is ours, not a debug-mode side effect. How can I see the raw SQL queries Django is running?

Shape of the code

Django’s own example is a logger object with __call__. A function that closes over a list is the same idea, smaller. Put the import at the top. Wrap the existing get_response line. This is a copyable shape; wiring it into middleware.py is yours. 

# Django's handle to the database for this thread.
from django.db import connection
# A clock. We use it to time how long each query took.
import time

# Empty list. Every query we see gets appended here.
queries = []

# Django calls this function once per SQL, while the wrapper is on.
# The five names are what Django always passes in.
def capture_sql(execute, sql, params, many, context):
    # Clock reading right now, before the query runs.
    start = time.monotonic()
    # Actually send this SQL to the database. Skip this and the
    # query never runs. result is whatever the database sent back.
    result = execute(sql, params, many, context)
    # Write one record into our list. This does not print anything.
    queries.append({
        # The SQL string. Placeholders like %s, not the real values.
        "sql": sql,
        # The values that fill those placeholders. A tuple becomes a
        # list. If Django passed nothing, store an empty list.
        "params": list(params) if params else [],
        # Milliseconds between start and now.
        "duration_ms": round((time.monotonic() - start) * 1000, 2),
    })
    # Hand the database result back unchanged.
    return result

# Turn the wrapper on, run the next line, then turn it off.
with connection.execute_wrapper(capture_sql):
    # Inner middleware + the view. SQL runs in here.
    response = self.get_response(request)

# Put the list onto captured so json.dumps prints it with the rest.
captured["sql"] = queries

Meaning: turn something on, run the indented block, then turn it off automatically. Python’s docs: the with statement wraps a block with setup and cleanup. Django’s execute_wrapper is that setup/cleanup: enter installs capture_sql, exit removes it. Cleanup still runs if the indented lines crash. The with statement · execute_wrapper is Python, not Django. On this line it means: install capture_sql, run get_response, then uninstall it. The indented line is the only window where Django will call your wrapper.

Two rules from the docs, both already true of middleware: call the next callable, and return what it returned. Skip execute and the request never reaches the database.

sql is a template with placeholders. params is the list of values. Keep them separate — do not glue the slug into the string. The type at this hop is still a Python list sitting next to a string.
