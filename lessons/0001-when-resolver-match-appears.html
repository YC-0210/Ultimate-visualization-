The path vs Django’s choice

You already know the URL the browser sent. You do not yet know which of your routes Django picked.

Where this fits Roadmap: Phase 1, P1.2 — capture the resolved route. Mission: the URL Router stage is Django’s decision, not the string in the address bar. Today’s win is seeing that those are two different facts, and that the decision does not exist yet at your current print.

What Django decided

Which pattern matched, what it is named, which view will run, which pieces came out of the path.

Same request. Different information. The first is what the customer typed. The second is the waiter looking at the menu and saying “that’s 經典原味鍋.”

P1.2 is capturing the waiter’s answer. Not adding more keys next to path on the same line. That line runs before Django has looked the path up, so the answer does not exist yet.

What “resolving a URL” means

Django’s docs say the waiter’s answer appears after URL resolving took place. That phrase is not a special kind of URL. It is Django doing a lookup.

You already wrote the menu: a list of patterns in urls.py. Each pattern says “if the path looks like this, run that view.” How Django processes a request is the algorithm: load that list, walk it in order, stop at the first pattern that matches the incoming path, then call that view. If nothing matches, it is a 404.

Resolving is that walk. Incoming string in, “this pattern, this view, these leftover pieces” out.

Those leftover pieces are how 經典原味鍋 becomes an argument the view can use. The path string does not know that; only the walk does. Django stores the Type: an instance of ResolverMatch. Django’s docs: “An instance of ResolverMatch representing the resolved URL.” That is the object for “this pattern, this view, these leftover pieces.” Stored on request.resolver_match. Set only after URL resolving. On a 404 with no matching pattern the attribute is missing — read with getattr(..., None). ResolverMatch · HttpRequest.resolver_match of the walk on the request as request.resolver_match.

Two different “menuitem” URLs in this project. Do not mix them. /api/menuitem/經典原味鍋/ is the JSON API (menuitemDetail, name menuitem_detail). /menuitem/經典原味鍋/ is the HTML page (menuitem_detail the function, name menuitem_page). This lesson uses the API one. Slugs come from the live database: 經典原味鍋, 廣式沙茶鍋 — not from the prototype.

When that result exists

The walk does not happen the instant the request arrives. Your current print sits above response = self.get_response(request). The walk happens inside that call. When it returns, the result is sitting on the same request. Read it then.

That is what the docs mean by after URL resolving took place: after the walk, not after the browser sent the path. The result is available in views, and in middleware process_view(). It is not available in middleware that runs before the walk.

Primary sources: How Django processes a request (what the walk is), ResolverMatch (the object the walk returns), and request.resolver_match (where that instance is stored). Django’s handler does the walk in BaseHandler.resolve_request.
