When resolver_match appears

P1.1 already prints method, path, headers, and body. P1.2 needs the resolved route — and that fact is not on the request yet at the line where you currently print.

Why this is the next capture

request.path is what the browser sent: /api/menuitem/classic-original/. The URL Router stage in the lab needs what Django decided: which pattern matched, what it is named, which view will run, and which kwargs came out of the path. Those live on request.resolver_match, a ResolverMatch.

If you put that read next to method and path, you will capture None (or hit AttributeError). That is not a bug in your dict. Django has not resolved the URL yet.

The one timing rule

From the docs, almost verbatim: the attribute is set after URL resolving took place. It is available in views, and in middleware process_view(). It is not available in middleware that runs before resolving.

Primary source: HttpRequest.resolver_match (Django 5.2; 6.1 says the same). Read that paragraph before you edit code.

Your middleware is a class with __call__. The middleware docs split that method at get_response(request): 

def __call__(self, request):
    # BEFORE — request phase. Path is here. Match is not.
    response = self.get_response(request)
    # AFTER  — response phase. Match is on the request now.
    return response

URL resolving happens inside get_response, after every middleware has had its inward (request-phase) turn. That is why P1.1's print cannot grow a route key in place.

The class-based view trap

    

      For a CBV, path(..., Menu.as_view()) stores the
      wrapper function as_view returned, not the class.
      match.func.__name__ is usually "view" — useless.
      Django documents that the wrapper carries
      view_class.
      Django Debug Toolbar names a view the same way:
      if func.view_class exists, use that class's
      module + __qualname__; otherwise use the function.
    

    

      Do not copy func.cls from the prototype.
      extract_all.py uses .cls, which DRF sets as an extra.
      Django's own name is view_class. DRF wrappers have both;
      a plain Django CBV has only view_class. Function views have neither.
    

    

      Unmatched 404s never resolve, so the attribute may be missing.
      Read it with getattr(request, "resolver_match", None)
      and skip the route block when that is None.
