OTel's Trace, and why a Stage is not a span

You already know your Trace holds stages. You do not yet know which parts of that shape OpenTelemetry defined and which parts this repo invented.

Where this fits Roadmap: Phase 1, P1.9 — the reshape. Lesson 0016 gave you kind and label. D5 borrowed OTel's tree; D6 kept the dependency. Today: read the borrowed definitions at the source, then see exactly where this repo departs from them. See where this sits on the map →

The problem

trace_id and parent_id are not words this repo coined. Stage is. One JSON object. Two vocabularies.

What OTel calls a Trace

OTel's one-line definition of a Type: one or more spans sharing a trace_id — Traces. OTel's docs: “The path of a request through your application.” And: “A trace is made of one or more spans. The first span represents the root span.” Tier 2 — a borrowed spec word, not Django's and not ours. Traces · Observability primer is “the path of a request through your application.” A Type: one timed unit of work — Spans. OTel's docs: “A span represents a unit of work or operation. Spans are the building blocks of Traces.” The spec lists what it encapsulates: the span name, a SpanContext, a parent, a SpanKind, start and end timestamps, attributes, links, events, and a status. Trace API — Span is one timed unit of work inside it.

OTel's docs walk three spans and then say what makes them one Trace: “These three blocks of JSON all share the same trace_id, and the parent_id field represents a hierarchy. That makes it a Trace!”

OTel's root span, trimmed to the fields that matter here

{
  "name": "hello",
  "context": {
    "trace_id": "5b8aa5a2d2c872e8321cf37308d69df2",
    "span_id": "051581bf3cb55c13"
  },
  "parent_id": null,
  "start_time": "2022-04-29T18:52:58.114201Z",
  "end_time": "2022-04-29T18:52:58.114687Z",
  "attributes": { "http.route": "some_route1" }
}

Two rules to keep from that object. OTel on the root: it “has a trace_id field indicating the trace, but has no parent_id. That's how you know it's the root span.” And the child hello-greetings carries “a parent_id that matches the span_id of the hello span.” That pair of ids is the whole tree mechanism — and it is exactly what D5 borrowed when it decided stages form a tree.

The attribute rule your spike already hit

OTel constrains what an Type: a key-value pair on a span — Attributes. OTel's docs: “Keys must be non-null string values. Values must be a non-null string, boolean, floating point value, integer, or an array of these values.” No dicts. No nesting. Attributes may hold: strings, booleans, floats, integers, or arrays of those. A dict is not on that list.

That single sentence is why P0.4a had to JSON-dump the {type, value} encoding into one string attribute instead of attaching validated_data directly. Your encode function exists because of this rule. And P0.4a's permanent finding follows from it: OTel does not raise on a nested value — it drops the attribute and logs a warning.

Where this repo departs

A span measures time. A Stage holds a shape. OTel: a span is “a unit of work or operation,” with a start and an end timestamp. CONTEXT.md: “A Stage is a location, not a step in time; the Packet is what moves between them.” Your mission is the type at each hop, not the millisecond count — so the Stage is the thing the panel needs, and the span is at best how it gets built.

Why not reuse SpanKind

OTel does have a closed enum called Type: one of five fixed values — SpanKind. The spec: “SpanKind describes two independent properties” — whether the span is an outgoing call or the processing of an incoming request, and whether it is request/response or deferred execution. Values: CLIENT, SERVER, INTERNAL, PRODUCER, CONSUMER. Default is INTERNAL. Trace API — SpanKind — five values, never extended. It is the right shape and the wrong subject.

The spec defines INTERNAL as spans for “operations which do not cross a process boundary. Things like instrumenting a function call or an Express middleware may use internal spans.” Now apply that to your own request.

Four different jobs, one SpanKind. It classifies messaging role, which is what a distributed backend needs; it says nothing about which job in the request lifecycle ran, which is the only thing the panel needs. That is the sentence in D7: the prior art is LSP's SymbolKind, not OTel's SpanKind.

The span name cannot do the job either. The spec: the name “SHOULD be the most general string that identifies a (statistically) interesting class of Spans,” and “get_user is a reasonable name, while get_user/314159 … is not a good name due to its high cardinality.” It is disciplined free text, not a closed list — so no panel can safely switch on it.

Not competitors — different layers. D6 keeps the OTel dependency for context propagation: a probe firing deep inside DRF parents itself under the request span with no manual threading. Nothing in your middleware.py imports opentelemetry today, and P1.9 does not need it. When stages do nest, a Stage becomes what you read off a finished span — not a rival to it.
