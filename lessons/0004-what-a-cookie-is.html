Whether they have been here before

A number on a ticket they kept. You already dump headers — look for Cookie.

Cookie: (none) → Cookie: sessionid=…

Same request. Different information. The path is what the customer typed. The ticket is how the waiter knows this is not a brand-new stranger. The waiter still looks the path up on the menu either way.

A cookie is that ticket — a number, not a name. The diner keeps it and puts it on the table next time. It is not who they are. It is how Django finds a dictionary of facts it stored on the server for this diner. Django’s docs call that dictionary a session.

Why a ticket exists at all

Each new order arrives as if the waiter has never seen you. Nothing in HTTP remembers the last visit by itself. MDN’s word for that is stateless: by default the protocol does not remember.

So the waiter writes a number on a ticket and hands it to the diner (the response header Type: an HTTP response header. Value is a name=value string, e.g. sessionid=abc…. MDN: after a request, “a server can send one or more Set-Cookie headers with the response.” The browser may store that pair and send it back later. MDN: Using HTTP cookies ). Next visit, the diner puts the same ticket on the table (the request header Type: an HTTP request header. Value is a string of name=value pairs the browser is sending back. MDN: the browser may “send them back to the same server with later requests.” That string is what you already print inside captured["headers"]. MDN: Using HTTP cookies ).

Django’s session docs say the same thing: “Cookies contain a session ID – not the data itself.” After you hit /?table_number=3, Django stores table_number in a dictionary on the server. The next page’s URL has no 3 in it. Django still knows 3 because the ticket number finds that dictionary. The ticket only has the lookup number, usually named sessionid.

Primary sources: MDN: Using HTTP cookies (what a cookie is, Set-Cookie vs Cookie, why HTTP needs this), How to use sessions (the ticket holds an id, not the stored facts). Card: cookie.html.

Do this on the restaurant app

No edit to middleware.py. You already print headers. Use the same browser for every step.

  1. Hit GET /api/menuitem/經典原味鍋/. In the print, look at headers. Is there a Cookie line? (Often none on a first hit.)
  2. In that same browser, hit GET /?table_number=3 (the homepage). That view writes table_number into the session dictionary. Django then hands back a ticket (Set-Cookie) — you will not see that header in today’s print.
  3. Hit the API URL again. The Cookie header should now contain sessionid= plus a string.
  4. Tell me whether Cookie was missing, then present. Then we go to P1.3: what the waiter reads off that ticket.
