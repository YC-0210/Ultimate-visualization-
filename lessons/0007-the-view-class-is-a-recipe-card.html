Read DRF configuration from the view class

You already capture which view class Django selected. You do not yet capture the DRF configuration declared on that class.

Where this fits Roadmap: Phase 1, P1.4 — capture the view class, permission_classes, serializer_class, and queryset model. P1.2 already found the class. Today you read three more facts from that same class. See where this sits on the map →

The problem

Same real request: GET /api/menuitem/經典原味鍋/. One route choice, two levels of knowledge.

Already have · P1.2

The selected view class

The resolved route points to this class.

restaurantAPI.views.menuitemDetail

Missing · P1.4

The class’s DRF configuration

Its permission policy, serializer class, and queryset model.

AllowAny · menuitemSerializer · menuitem

One short analogy for the new idea: the view class is like a recipe with its access rule, data translator, and ingredient type written on it. P1.4 reads those declarations. From here on, we will use their real names.

Capture names, not live Python objects. The permission, serializer, and model are Python classes. The queryset is a Python object. None can go directly into JSON. Store each class as its module plus qualified name.

Where the three facts live

P1.2 gave you view_class. DRF’s generic-view docs call queryset and serializer_class class attributes. Its permission docs say permission_classes sets the policy per view.

Read from view_class

permission_classes

A list of permission classes, not the result of a permission check.

[rest_framework.permissions.AllowAny]

Read from view_class

serializer_class

The class DRF uses to serialize and deserialize data.

restaurantAPI.serializers.menuitemSerializer

The third fact takes one extra peel: view_class.queryset is the Type: an instance of django.db.models.query.QuerySet. Django describes a QuerySet as a collection of database objects. Here, read only its model attribute. QuerySet API reference . Its .model is the menuitem class. 

view_class
  ├── permission_classes  → list of classes
  ├── serializer_class    → class
  └── queryset            → QuerySet object
         └── model        → class

Do not run the queryset

cartitemList has both a class-level queryset and a get_queryset() method that filters rows using the current user or session. P1.4 asks only which model the view works with: cartitem.

Do not call get_queryset(), loop over the queryset, or turn it into a list. Those actions can run application logic or SQL. Reading queryset.model returns the model class without evaluating the queryset.

Shape of the code

Put the helper above the middleware class. Put the capture inside your existing if view_class is not None: branch. This is a copyable shape; wiring it into middleware.py is yours. 

def class_name(value):
    if value is None:
        return None
    return value.__module__ + "." + value.__qualname__


# Inside: if view_class is not None:
captured["permission_classes"] = [
    class_name(permission)
    for permission in getattr(view_class, "permission_classes", [])
]

serializer_class = getattr(view_class, "serializer_class", None)
captured["serializer_class"] = class_name(serializer_class)

queryset = getattr(view_class, "queryset", None)
model = getattr(queryset, "model", None)
captured["queryset_model"] = class_name(model)

getattr(..., None) matters because plain Django function views do not promise these DRF attributes. A missing serializer or queryset becomes JSON null, not a server crash.
