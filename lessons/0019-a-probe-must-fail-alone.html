A probe must be able to fail alone

Your middleware reads facts off every request. It can also stop a request that would otherwise have worked.

Where this fits Roadmap: Phase 1, P1.10 — the last task in the phase, and marked 🔴. Lesson 0018 put the Trace on disk. Today the reads that build it stop being able to take the app down with them. Phase 2 opens the panel in a browser tab; a tool that 500s the app it is watching does not get opened twice. See where this sits on the map →

The problem

Loading one page sends more than one request. Two of them reach your middleware: the page, and the image on it. One of those two is broken right now, and your middleware is what broke it.

Works · verified today

GET /menuitem/經典原味鍋/

200. Five stages, five queries, a Trace file on disk.

status 200 · HttpResponse

Broken · verified today

GET /media/menu/images.jpeg

The <img> on that same page. 500, from your middleware, not from the app.

AttributeError · no `content`

That second row is not hypothetical and it is not a future worry. It is the image on the page you have been practising on. The template asks for it: 

<img src="{{ item.image.url }}" alt="{{ item.product }}">

經典原味鍋's image column holds menu/images.jpeg, so the browser requests /media/menu/images.jpeg, and the exception raised is: 

AttributeError: This FileResponse instance has no `content` attribute.
Use `streaming_content` instead.

Why that line raises

Your project's root urls.py ends with urlpatterns += static(settings.MEDIA_URL, …), so media files are matched by a route and served by a view — which means they travel the whole middleware stack, yours included. This is also why you have not tripped over it before: /static/ is intercepted by runserver's StaticFilesHandler before the middleware chain begins, so stylesheets never reach you. /media/ is an ordinary route, so it does. That view returns a Type: a subclass of StreamingHttpResponse, not of HttpResponse. Django's docs: StreamingHttpResponse “should only be used in situations where it is absolutely required that the whole content isn't iterated before transferring the data to the client.” It “has no content attribute. Instead, it has a streaming_content attribute.” The docs add that middleware “should not” consume that attribute. FileResponse · Dealing with streaming responses .

Reading .content on it does not return an empty value or None. Django deliberately raises, and the message tells you the replacement attribute. Your lesson 0009 line catches UnicodeDecodeError, which is the wrong exception — so it escapes, and Django turns it into a 500 for a request that had a perfectly good image ready to send.

The response object is not one type. HttpResponse.streaming is False and StreamingHttpResponse.streaming is True. Django documents that flag precisely so middleware can tell them apart before touching the body. Check the flag; do not guess from the status code or the path.

Where the guard goes

P1.10 says “wrap every hook in try/except”. The whole task turns on how much each wrap covers. Click through the three placements.

Placement 2 is worth being precise about, because the obvious argument against it is wrong. You might expect a wide try to swallow the view's own errors — it does not, and Django's docs say why:

“This conversion takes place before and after each middleware … so that every middleware can always rely on getting some kind of HTTP response back from calling its get_response callable. Middleware don't need to worry about wrapping their call to get_response in a try/except … Even if the very next middleware in the chain raises an Http404 exception, for example, your middleware won't see that exception; instead it will get an HttpResponse object with a status_code of 404.”

Django: Middleware — Exception handling

So the view's exception has already become a response by the time your code resumes. Guarding get_response is not dangerous so much as pointless — and actively harmful in one way: if the wide guard ever does fire, response was never assigned and return response fails. The only escape is to invent a response the app never produced, which is a tool writing the output it claims to be observing.

The same paragraph also explains the 500 you can reproduce today: “an exception raised from a middleware will immediately be converted to the appropriate HTTP response.” Django does not distinguish your probe's AttributeError from a real failure. Nothing outside your middleware can make that distinction for you — which is why the guard has to be inside it.

Call the original outside the guard. Guard only what you do with the result. A probe that swallows the exception it was watching has stopped observing and started editing.

Your two monkeypatched probes already have the first half of this right. probed_is_valid and probed_render both call the original on their first line and only then append, and the finally restore is already in the right place (lesson 0013). What is missing is the guard around the append itself: if encode() raises on some value it has not met before, that exception surfaces from the middle of DRF's is_valid.

Inside the view, Django's safety net is not there. The paragraph above applies at the middleware boundary. Your two probes run somewhere else — deep inside get_response, in the app's own call stack. An exception from probed_render's append does not arrive at your __call__ as a tidy 500 response; it arrives inside the view, at the line that called render. That is why these two sites need their own guards even though the response read is guarded separately.

except Exception, not bare except

Python's docs on the class: “All built-in, non-system-exiting exceptions are derived from this class.” The exclusion is the point. KeyboardInterrupt and SystemExit derive from BaseException instead, so they pass straight through except Exception.

A bare except: catches those too. In a middleware that runs on every request, that means Ctrl-C on runserver gets eaten by your probe's error handler.

Silence is a lie in this schema

This is the part of P1.10 the roadmap line does not say out loud. “Drop the trace on failure” is only half a design, because in lesson 0016 you decided that an absent stage means something: your POST /api/cart/item/ Trace has no render_output, and that absence is a true fact — no template rendered.

So if a guard swallows a failure without a trace of its own, the panel reads the same absence and reports the same fact — except this time it is false. The template did render; your probe fell over. That is exactly what D2 forbids: the displayed facts have to be things the code observed.

Swallow, then leave a mark. A guard that fires appends to a capture_errors list on the Trace. Absence keeps meaning “did not happen”; a named failure means “happened, not captured”. Two different facts need two different shapes in the file.

This is what shipped instrumentation does. The Sentry SDK wraps its own internals in capture_internal_exceptions(), whose __exit__ returns True — Python's signal to suppress — and hands the exception to a function whose docstring reads “Capture an exception that is likely caused by a bug in the SDK itself. These exceptions do not end up in Sentry and are just logged instead.” Swallowed from the host application; recorded for the tool's author. Both halves.

Same, with a comment on each line

import logging
# Standard library. The mark goes to the console as well as into the file,
# so you notice a broken probe while developing it.

logger = logging.getLogger("supervisualizer")
# Module level, named for the package. Django configures the root logger,
# so this prints under runserver without further setup.


# inside __call__, near the top
capture_errors = []
# Per request, like queries and validations. Not module level, or two
# requests share one list.

def note_failure(where, exc):
    capture_errors.append({
        "where": where,
        # Which hook fell over: "response", "sql", "serializer", "trace".
        "error": type(exc).__name__ + ": " + str(exc)[:200],
        # The class name is the useful half. str(exc) can be huge, so cap it,
        # same reason encode() caps values at 200.
    })
    logger.warning("[supervisualizer] capture failed at %s", where, exc_info=True)
    # exc_info=True prints the traceback. warning, not error: the request
    # itself succeeded.


# the response read, replacing your current try/except
if response.streaming:
    # Django documents this flag: False on HttpResponse, True on
    # StreamingHttpResponse. Check it BEFORE touching .content, because
    # reading .content is what raises.
    response_body = "<streaming response; body not read>"
    # A recorded fact, not a guess: we chose not to read it. Django's docs
    # say middleware must not consume streaming_content — the client needs it.
    response_size = None
    # No byte count without reading the body. None, not 0: 0 would be a lie.
else:
    try:
        response_body = response.content.decode("utf-8")
    except UnicodeDecodeError:
        # Still the right exception for this one narrow case: real bytes
        # that are not UTF-8 text.
        response_body = f"<binary {len(response.content)} bytes>"
    response_size = len(response.content)
    # Byte length of content, as in lesson 0009. Only legal in this branch.

captured["response"] = {
    "status": response.status_code,
    # Safe on both types: status_code is on HttpResponseBase, the shared parent.
    "headers": dict(response.headers),
    # Also on the shared parent. A streaming response still has headers.
    "body": response_body,
    # Now a name from the branch above, not a second read of .content.
    "size": response_size,
    # This is the line that changes: it was len(response.content).
}


# every site that is bookkeeping, including the file write
try:
    ...
except Exception as exc:
    # Exception, not a bare except: Ctrl-C must still stop runserver.
    note_failure("response", exc)
    # Swallowed here. The request carries on and `return response` is reached.


# and on the trace, beside notes
"capture_errors": capture_errors,
# Usually []. When it is not, the panel can say "not captured" rather than
# letting a missing stage read as "did not happen".
