Why that order, twice

Inward the diner walks down the list. Outward they walk it backwards. Later names need pockets earlier names just filled.

door first-in last-out · Auth after Session

This is not a chore list that runs once from top to bottom and stops. It is a line of waiters between the door and the kitchen. Each waiter has one job. Each can stamp a pocket on the same ticket — the Type: an instance of django.http.HttpRequest. Same object you already dump. Middleware and the view all receive this one visit. HttpRequest — then send the diner to the next waiter.

That “send them on” call is get_response. Django’s docs: it might be the next middleware, or eventually the view. You already wrote this in middleware.py: print, call self.get_response(request), print again.

What one middleware is

Django’s docs: middleware is a plugin for globally altering input or output. Each component does one specific function. Example they give: AuthenticationMiddleware associates users with requests using sessions.

A middleware takes a request and returns a response — the same shape as a view. The difference: before it returns, it usually calls Type: a callable. You call it with request; it returns a response. Django’s docs: “The get_response callable provided by Django might be the actual view (if this is the last listed middleware) or it might be the next middleware in the chain.” Writing your own middleware .

Django’s docs call the wrapping an onion: each class is a layer around the view. Request phase: top-down. Response phase: reverse. Middleware order and layering.

Why Auth is after Session

Django’s docs, twice: the order in MIDDLEWARE matters because a middleware can depend on other middleware. AuthenticationMiddleware “stores the authenticated user in the session; therefore, it must run after SessionMiddleware.” The ordering page says the same thing shorter: “After SessionMiddleware: uses session storage.”
