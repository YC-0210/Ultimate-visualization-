The map

Everything at once: the journey one request takes, what is captured today, what is being built now, and what has not been observed yet — with every lesson and reference card hung off the stage it explains.

Capture is deterministic. The LLM explains; it never observes.

The value is that the numbers are real, because real code produced them. Unplug the model and the tool must still capture and display everything correctly — just without prose.

If I can't see it all at once, I don't understand it yet.

A part understood in isolation is a part you will lose. Anything that can only be read one moment at a time — a step debugger, a directory of twenty-one lessons — moves the assembly work into your head, which is where the understanding was supposed to end up. This page exists because of this principle, and is the first test of it.

1 · The journey

The fourteen kind values are the closed, framework-neutral vocabulary from P0.4 — the job a stage does, independent of what Django calls it. Scrub across them. Past means the stage is emitted into a Trace today and the values shown were really produced. Future means nothing has observed it yet — so the panel shows no data rather than a plausible guess (D2).

Values below are from the real POST /api/cart/item/ trace recorded at P1.9. Tick All at once to stop scrubbing and see the whole journey open at the same time.

What the journey shows that no single lesson does

  • Three kinds in the vocabulary have never appeared in a Trace. authorize, query_data and mutate_data all have their facts captured, but none is emitted as a stage — the SQL sits in a flat list at the top of the Trace and permission_classes is folded into route.
  • Every stage in today's Trace has parent_id: None. D5 chose a tree over a flat list specifically so the SlugRelatedField SQL could nest inside validate_input. The tree exists in the schema and not yet in the data.
  • The server half is five of fourteen kinds. Nine-fourteenths of the journey the mission describes is Phase 4, and it is the half that carries both type hops the mission names by hand.

The seam: everything right of the panel talks to it only through the Trace schema. Django is one Adapter producing that schema. Framework #2 is a new adapter, not a new tool. Get the schema right in Phase 1 and Phase 6 is easy; get it wrong and Phase 6 is a rewrite.

Why the browser reports separately: Django only ever sees the middle of the story. The "2" → 2 hop happened before the request left; res.json() happens after the response was sent; a client-only interaction produces no request at all. None of those can ride on the response, so the probe posts its own half and the server joins the two by trace id.
