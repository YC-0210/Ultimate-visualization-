# Spike P0.4a — can OpenTelemetry carry our values?

**Status: DONE. Verdict — PASS, keep the dependency.** But for a different reason than D6 assumed, and two of D6's claimed benefits turned out to be false. See [Results](#results).

**Blocked:** Phase 1. Now unblocked.
**Code:** [`P0.4a-code/`](P0.4a-code/) — run against `restautant-order-system`, kept as evidence.

---

## The question

We decided to build on OpenTelemetry. OTel spans carry **attributes**, and attribute values may only be a string, number, boolean, or a flat sequence of those. **Nested objects are not allowed.**

Our data is nested objects. That is not incidental — it is the thing the tool exists to show:

```python
validated_data = {
    "product":            <menuitem: classic-original>,
    "meattype":           <meattype: beef-short-plate>,
    "hotpotingredients": [<hotpotingredients: squid>],   # list of objects
    "quantity":           2,
}
```

So: **is OTel a foundation we can build on, or only a shape worth copying?**

Both answers are useful. The bad outcome is finding out in Phase 6.

---

## Already verified — do not spend time re-checking

Run against `opentelemetry-sdk` with a custom `SpanProcessor` reading spans in-process.

### 1. 🚨 Invalid attributes are dropped **silently**

This is the finding that matters most, and it changes how you must test.

```python
span.set_attribute("validated_data", {"a": {"b": 1}})   # nested dict
# → NO exception raised.
# → a warning goes to the `opentelemetry.attributes` logger
# → the attribute is simply ABSENT from the finished span
```

Same for a list of dicts, and for `span.add_event(name, {...nested...})` — there the event survives but arrives with **empty attributes**.

**Consequence for this spike, and for all later work:** never conclude something worked because no exception was raised. Always assert on what is actually present on the finished span. A test that only calls `set_attribute` and checks for no error will pass while losing every value.

### 2. The JSON-string workaround is not size-limited by default

```python
span.set_attribute("validated_data", json.dumps(...))   # works
```

- A 35,400-character JSON string survived intact, untruncated.
- `SpanLimits.max_attribute_length` defaults to `None` — no truncation unless configured.
- Limits that *do* exist: **128 attributes** and **128 events** per span.

So the workaround is mechanically viable. Whether it is *desirable* is the actual question.

### Reproduction

```python
import json, logging
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider, SpanProcessor

captured = []
class Grab(SpanProcessor):
    def on_end(self, span): captured.append(span)

tp = TracerProvider(); tp.add_span_processor(Grab())
trace.set_tracer_provider(tp)
tracer = trace.get_tracer("spike")

nested = {"product": "<menuitem: classic>", "quantity": 2,
          "hotpotingredients": [{"slug": "squid", "price": "40.00"}]}

with tracer.start_as_current_span("validate") as s:
    s.set_attribute("validated_data", nested)             # dropped
    s.set_attribute("validated_data_json", json.dumps(nested))   # kept

print(dict(captured[0].attributes))   # only the _json key is there
```

## What is actually left to find out

The factual question is closed: OTel cannot hold nested values, and JSON-encoding works. What remains is judgement, and four unknowns you can only learn by doing.

### U1 — Do our real values even survive `json.dumps`?

They will not, unencoded. `<menuitem: classic-original>` is a Django model instance; `Decimal("320.00")` is not JSON-serialisable either. You need an encoder that turns arbitrary Python objects into `{type, value}` pairs — which is exactly what `jsonable()` does in `../../prototype/extract_all.py`. Port that idea and see how much of it survives contact with objects you did not anticipate.

### U2 — What does it look like in a real Django request?

The verified findings above are from a bare SDK. Install `opentelemetry-instrumentation-django`, point it at `restautant-order-system`, hit `POST /api/cart/item/`, and look at the spans that come out. Specifically: do you get a usable tree (request → view → DB), and is there a sensible span to hang `validated_data` on, or do you have to create your own?

### U3 — Is one span enough, or do you need many?

128 attributes per span. If every stage's data becomes its own JSON attribute on one big span, you will be fine. If you instead want a span per stage — which is the tree shape we already chose — then you need to create child spans yourself, and the question becomes how naturally OTel's context propagation lets you do that from inside a serializer probe.

### U4 — 🔑 The real one: what is OTel still buying you?

If every value rides as an opaque JSON blob that OTel itself cannot interpret, then OTel is contributing the **tree, the timing, the parent/child links, and free Django+DB instrumentation** — and nothing at all about the data. That may be a perfectly good deal. It may also be a lot of dependency for a data model you are carrying yourself.

Answer this one explicitly. It is the decision the whole spike exists to inform.

## Steps

1. Fresh venv. Install `opentelemetry-sdk`, `opentelemetry-instrumentation-django`, and the restaurant project's requirements.
2. Reproduce the silent-drop behaviour yourself. Seeing an attribute vanish with no error is worth ten minutes — it will inform how you write every probe later.
3. Instrument the restaurant project. Get *any* span out of a real request.
4. Write the object encoder (U1) and attach one real `validated_data` to a span as JSON.
5. Read it back off the finished span in your `SpanProcessor` and assert it round-trips **field by field**, not just "is present".
6. Try one span per stage (U3) and see how it feels.
7. Write down the answer to U4 in a sentence.

---

## Pass / fail

**Pass — keep the dependency.** One approach is comfortable, real values round-trip intact, the Django instrumentation gives a usable tree, and U4 has a convincing answer. Proceed to Phase 1 building on OTel.

**Fail — keep the shape, drop the dependency.** You are writing more code to work around OTel than it saves, or context propagation fights the probes, or U4 comes back as "not much". Then supervisualizer keeps spans-as-a-tree, `trace_id`, `parent_id` and the semantic-convention discipline, and emits its own JSON. The Trace schema barely changes; only the plumbing does.

**Either result closes P0.4a.** There is no outcome where the afternoon was wasted.

# Results

Run against the real `restautant-order-system` with `opentelemetry-sdk 1.44.0`,
`opentelemetry-instrumentation-django 0.65b0`, Django 6.1, DRF 3.18.

## Verdict

**PASS — keep the dependency.** But D6's stated reasoning was wrong in two places,
and the thing that actually justifies OTel is something D6 never mentioned.

## What passed

**U1 — values round-trip.** A `{type, value}` encoder (ported from the prototype's
`jsonable()`) JSON-encoded into a single string attribute survives intact. Real
`validated_data` from `POST /api/cart/item/`:

```
product              type=menuitem instance      <menuitem: classic-original> pk=1
meattype             type=meattype instance      <meattype: beef-short-plate> pk=1
hotpotingredients    type=list                   [{hotpotingredients instance...}]
quantity             type=int                    2
doublemeat           type=bool                   True
notes                type=str                    少辣不要蔥
```

All keys present, model instances preserved with their fields, non-ASCII intact,
743 characters. No truncation.

**U3 — a span per stage works.** Nesting `start_as_current_span` produces the
D5 tree with correct `parent_id`s and one shared `trace_id`, for free.

**🔑 The real finding — context propagation crosses the framework boundary.**
Probes monkeypatched into DRF's `Serializer.is_valid` and `BaseSerializer.save`,
firing deep inside a real request, produced spans that **automatically parented
under Django's request span** with zero manual context threading:

```
- POST api/cart/item/                              ← DjangoInstrumentor
  - validate_input   [sv.kind=validate_input]      ← our probe, 470ch of data
    - mutate_data    [sv.kind=mutate_data]         ← our probe, nested correctly
```

`context propagation across the framework boundary: WORKS`

This is what OTel is genuinely worth. Building it ourselves means contextvars,
a span stack, and correct behaviour under async and threads. It is real work,
easy to get subtly wrong, and OTel has already done it.

**Overhead — negligible.** 2.13 ms vs 2.06 ms per request, **+3%**. Not a concern
for a dev tool.

## What failed — two D6 claims were wrong

**❌ "Free Django instrumentation" is one span.** `DjangoInstrumentor` produces
exactly **one** span per request, carrying `http.method`, `http.route`,
`http.status_code`, `http.url`. Useful, but it is the request boundary and nothing
more — no view internals, no serializer stages. Every stage that matters is ours
to build.

**❌ "Free DB spans" do not exist for Django.** `SQLite3Instrumentor` installs
cleanly and then captures **zero** ORM queries — Django's ORM goes through its own
connection wrapper, which `sqlite3` instrumentation never sees. Use Django's
`connection.execute_wrapper` and create spans by hand, as P1.5 already planned.

**⚠️ Confirmed: silent drops.** `set_attribute("sv.data_raw", <dict>)` logged a
warning and the attribute was simply absent from the finished span. No exception.
Any probe that checks only for the absence of an error will pass while losing
everything.

## U4 — so what is OTel actually buying?

| | |
|---|---|
| ✅ **Context propagation and automatic parenting** | The reason to keep it. Non-trivial to build correctly. |
| ✅ Span tree, ids, timing | Exactly D5's shape, for free |
| ✅ `trace_id` | Needed anyway for the Phase 4 client/server stitch |
| ⚠️ Django instrumentation | One span with HTTP attributes. Small, but real. |
| ❌ DB spans | Not for Django's ORM. Build it. |
| ❌ Anything about the values | All our data rides as opaque JSON it cannot read |

The honest summary: **OTel is a context-propagation library we are using as one,
plus a tree format.** It is not an instrumentation shortcut. Nearly every stage
supervisualizer shows will be a probe we write.

That is still a good deal — but adopt it with those eyes, and do not expect
framework #2 to arrive cheaply just because OTel supports that framework.

## Consequences for later phases

- **P1.5** — write the DB probe with `connection.execute_wrapper`. Do not wait for OTel.
- **P1.7** — the monkeypatch pattern in `02_probe_integration.py` is the working
  approach for the serializer probe. It is proven; start from it.
- **P1.10** — silent drops make "no exception" worthless as a health signal.
  Assert on what is present on the finished span.
- **P6** — OTel supporting FastAPI buys you one HTTP span there too. The adapter
  is still most of the work.
